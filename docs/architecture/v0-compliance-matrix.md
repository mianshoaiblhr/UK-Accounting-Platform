## 1. Method and evidence rules
1. **Behaviour over files.** A row is IMPLEMENTED only if code *and* a passing test (or a verified command) demonstrate the behaviour. A table, route or document existing is not evidence.
2. **Evidence levels are kept apart** (see §2): unit/integration tests against real PostgreSQL and Redis; tests against a **moto S3 emulator**; tests against a real `clamd` daemon; Terraform **validation**; and — not yet done — anything on **real AWS**.
3. Claims were re-checked during this review rather than inherited from earlier reports: the dependency audit was run (`pnpm audit --prod`), the repository was scanned for secret patterns, the Terraform was read for what it provisions, X-Forwarded-For behaviour behind the Next.js rewrite was reproduced with a live echo server, and counts of tests/operations were recomputed.
4. Risk is stated as **Critical / High / Medium / Low** plus the impact in a sentence. "High (design)" means cheap now, expensive after V1 data exists.
5. IDs: `MAN-*` Manifest, `V0-<section>.<n>` V0 specification, `XP-*` cross-platform, `OBS-*` observability breakdown, `REV-*` additional review findings.

## 2. What the evidence does and does not prove
| Question | Answer |
|---|---|
| Are S3 tests real? | **No.** All S3 tests (`tests/infra/*`) run against **moto**, an S3-protocol emulator (locally and in CI; MinIO is no longer distributed). They prove the adapter speaks the S3 API and that our pipeline works end-to-end. They do **not** prove signature enforcement/expiry, SSE-KMS with our key policy, Object Lock, bucket policy, CORS or the VPC-endpoint path. **Real-AWS S3 validation has never been performed.** |
| Is ClamAV real? | **Yes** — CI uses the official `clamav/clamav` image with the live signature database; `clamd` detected EICAR (`Eicar-Test-Signature FOUND` in the service log). Not provisioned in AWS (REV-08). |
| Does Terraform "pass"? | `terraform fmt -check`, `init -backend=false` and `validate` pass (local + CI). This proves syntax, types and references. **Nothing has been planned against an AWS account, applied, or probed.** Expect first-apply surprises (quotas, IAM, KMS policy, naming, SES). |
| Was anything deployed? | **No.** There is no running AWS environment. TLS, encryption at rest, backups, DR, WAF, SES delivery and ECS runtime behaviour are therefore *configured, not verified*. |
| What does green CI #7 prove? | Build, lint, typecheck, 459 unit/integration tests (real PG 16 + Redis, password auth), 4 real-browser e2e tests, 29 adapter/pipeline tests (2 skipped by design), all migrations applied from scratch with the production script, Terraform validate, and 4 Docker images building. |
| What is not covered by any automated test? | Real AWS; accessibility; performance/load; restore/DR; SES delivery; multi-instance behaviour (more than one API/worker task); browser coverage beyond one Chromium journey. |

## 5. Requirements missed because the specifications were not available when V0 was built
V0 was implemented from the 17 architectural rules and the user's decisions. Against the specifications this left out: **core master data** (contacts, addresses, officers, currencies, countries, tax jurisdictions, year-end); the **Practice hierarchy level**; the **specified generic workflow states** and workflow **evidence / reassignment / SLA**; **task reviewer, comments, attachments, reminders and source**; **document folders, accounting-period link, document types, per-document permissions, filing-evidence class**; **audit before/after, reason, source workflow**; **OCRProvider and Embedding/Search provider**; **notification channel abstraction**; **device management**; **feature flags**; **evidence graph**; **configurable retention**; **metrics/tracing**; and **usable UI for the foundations**. Conversely, three things the user directed that the specifications do not require — the transactional outbox, OpenAPI generation, and layered login throttling — were built and are compatible with the specification's event, API-documentation and security intent.
