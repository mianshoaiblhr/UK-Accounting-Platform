# V0 Tranche A — completion log

Approved scope (V0 completion only, no V1): supply-chain scanning, audit framework, feature flags, outbox hardening, master data, task engine, document management, observability. Each increment records what was built, the design decisions (with the reason), behaviour changes and known limits. Decisions follow ADR-22…27; new ones are ADR-28 onwards in `adr.md`.

## 1. Supply-chain security scanning
See `docs/runbooks/supply-chain.md`. `pnpm audit --audit-level=high` is a CI gate (zero known advisories after the fix), gitleaks scans the full history, CodeQL runs on push/PR/weekly, Trivy scans every image, dependency-review blocks risky PRs, Dependabot opens update PRs. Overrides: `postcss`, `deepmerge-ts`; Vitest upgraded to 4.1.x (removes `tinypool`).

## 2. Audit framework (specification §8)
| Requirement | Implementation |
|---|---|
| actor, action, entity, timestamp | unchanged (`audit_event`, append-only) |
| before / after | `before`/`after` JSONB, **changed fields only** (`changeSet`), redacted, ≤ 16 KB in code (oversize → marker) and ≤ 32 KB by DB check |
| reason | `reason` (≤ 1000). Accepted on: member suspend (body) and remove (query), document archive (body), practice/company access removal (query), integration revoke (query). Optional, to stay backward compatible; workflow comments are recorded as the reason of their transition |
| source workflow | `source_workflow_id`. The workflow engine writes an audit event for every start / transition / reassignment; `ai.proposal_applied` carries the proposal's workflow. Filter: `?sourceWorkflowId=` |
| IP / device where lawful | captured by default for security events; `AUDIT_CAPTURE_DEVICE_METADATA=false` removes IP and user agent from **every** audit event (actor, time, correlation id are kept) |
| company dimension | `company_id` on events (DB trigger: must be a company of the event's organisation; no FK so the trail outlives its subjects) |

**Decision (ADR-28): `audit:read` moved from ORG to COMPANY scope.** Previously anyone with `audit:read` saw the whole organisation's trail, which defeated per-company least privilege. Now a company-level auditor sees only that company's events; organisation-level events (no company) need `audit:read` on the organisation role. Role contents are unchanged. Consequence for anti-escalation: only someone who holds `audit:read` on a company can grant a role containing it there.
Limits: events written before this change keep `company_id = NULL` (the trail is immutable, so they are not back-filled) and are therefore treated as organisation-level.

## 3. Transactional outbox hardening
| Concern | Implementation | Verified by |
|---|---|---|
| Ordering | `seq` identity column; the relay publishes only an aggregate's **head** (no earlier unprocessed event of the same `aggregate_type`+`aggregate_id`); the event bus refuses (`OutOfOrderEventError`, retried with backoff) to run an event while an earlier one is unprocessed. `processed_at` is set when every consumer committed | `tests/platform/outbox-hardening.test.ts` (head-only publication, failing head blocks only its aggregate, FAILED blocks until replay, concurrent relays, consumer guard) |
| Cleanup | `OutboxRelay.cleanup(retentionDays)` deletes events processed more than `OUTBOX_RETENTION_DAYS` (default 14, min 1) ago and their `event_consumption` markers, in bounded batches, every `OUTBOX_CLEANUP_MS` | same file (retention, batches, markers kept for recent events) |
| Safety of cleanup | `DELETE` is system-context only (RLS) and a trigger rejects deleting any event with `processed_at IS NULL`, whatever its age | same file + `tests/platform/outbox.test.ts` |
| Lag / backlog | `OutboxRelay.stats()` → pending, failed, in-flight, oldest unprocessed age (the *outbox lag*), oldest pending age. Exposed as metrics/alarms in increment 8 | same file (`stats`) |
| Bookkeeping | `processed_at` allowed only on `PUBLISHED` rows (check); `seq` immutable (identity `GENERATED ALWAYS` + trigger) | same file |

**Decision (ADR-29): ordering is guaranteed per aggregate, not globally.** Events of one aggregate are produced one after another because the business change holds the aggregate's row lock / optimistic version until commit, so insertion order is business order. Global order across aggregates is not promised (and not needed). **Liveness trade-off:** a poisoned head event (FAILED, or a consumer that keeps failing) blocks *its own aggregate* until an operator replays it (`replayFailed`) or retries the dispatch job; other aggregates continue and the blocked state is visible as `failed` / `oldestUnprocessedAgeSeconds`. Behaviour change: the app role may now `DELETE` outbox rows through RLS (system context only) instead of never.

## 4. Feature flags (Manifest cross-version rule; cross-platform §9)
* **Registry in code** (`@uk/contracts/features`): `ai.beta`, `documents.ocr`, `tax.rules.next`, `hmrc.endpoints.new`, `filing.formats.new`, `reporting.standards.new` - every flag has a description and defaults **off**. A flag that is not declared cannot be read, set or configured (typos fail at boot or return 404).
* **Resolution:** per-organisation override (table `feature_flag_override`, RLS) > environment default (`FEATURE_FLAG_DEFAULTS="key=true,..."`, validated at startup) > registry default. Per-process cache `FEATURE_FLAG_CACHE_MS` (default 5 s): a switch-off reaches every instance within that window; local changes invalidate immediately.
* **API:** `GET /feature-flags` (any member), `PUT|DELETE /feature-flags/{key}` (`org:manage`, i.e. owner), audited with before/after and reason. `@RequireFeature(key)` guards routes (403 `feature_disabled`); background work re-checks at execution time (queued AI requests stop when `ai.beta` is switched off).
* **Behaviour change:** `POST /ai/suggestions` now requires `ai.beta`, which is off by default in production (AI is "beta" per the specification). Tests enable it through `FEATURE_FLAG_DEFAULTS`. No production AI provider is configured today, so no live capability is lost.
* **Scope decision (documented, not a limitation of the model):** flags are organisation-wide; per-company flags can be added without changing the registry if a later version needs them.

## 6. Task engine (specification §5)
| Spec item | Implementation | Verified by |
|---|---|---|
| owner | `assignee_user_id` is the task **owner** (the person doing the work); `created_by_user_id` is the creator. The assignee must be an active member who can read the task's company | `tests/api/foundations.test.ts`, `task-engine.test.ts` |
| reviewer | `reviewer_user_id` (optional, never the assignee - check constraint; must be an active member with access to the company). New status **`IN_REVIEW`**. With a reviewer a task is completed **only from `IN_REVIEW` and only by that reviewer** (`POST /tasks/{id}/review`: `APPROVE` → `DONE`, `RETURN` → `IN_PROGRESS` with a mandatory comment). Enforced by the API **and** by a database trigger that reads the acting user from the tenant context, so a bypassed API still cannot self-approve. The reviewer cannot be changed during review or after completion | API test (flow, rights, DB bypass), `tests/db/task-engine.test.ts` |
| due date, priority, status | unchanged fields; status set is OPEN, IN_PROGRESS, IN_REVIEW, DONE, CANCELLED. Filters: status, assignee, reviewer, company, priority, source, `dueBefore`, `overdue` | API test (filters) |
| company | composite FK `(organisation_id, company_id)` added (was a bare column); per-company authorisation unchanged | `task-engine.test.ts` (db + isolation) |
| source | `source` (MANUAL, WORKFLOW, AI_PROPOSAL, DOCUMENT, EVENT, SYSTEM) + `source_id`. Clients may declare MANUAL/WORKFLOW/AI_PROPOSAL/DOCUMENT; the id must exist in the tenant and belong to the **same company**; EVENT/SYSTEM are reserved for platform-created tasks | API test (source) |
| attachments | `task_attachment`: link to a document of the **same company** (trigger; organisation-level tasks link organisation-level documents), unique per task+document, document must be ACTIVE and readable by the caller; the list shows document names only to callers who can read documents | API + DB tests |
| comments | `task_comment`: **append-only** (trigger + no `UPDATE`/`DELETE` grant), kinds COMMENT / REVIEW_APPROVED / REVIEW_RETURNED. Managers, the assignee and the reviewer may comment; any reader may read. Participants are notified | API test |
| reminders | `task_reminder` (recipient, `remind_at`; pending → sent \| cancelled exactly once, immutable target/time). Delivered by the worker's `TaskReminderSweeper` every `TASK_REMINDER_POLL_MS` | API + `tests/platform/task-reminders.test.ts` |

**Decision (ADR-31): reminders are swept, not queued.** A reminder is a row. The sweeper lists due reminders in the trusted system context (a read-only `SELECT` policy), then handles each one in its **own tenant transaction**, claimed with `FOR UPDATE SKIP LOCKED` and re-validated, so N workers deliver each reminder exactly once and the notification commits atomically with `sent_at`. A reminder for a task that is DONE/CANCELLED is cancelled, not sent. This survives Redis loss and needs no per-reminder delayed job. **Privacy rule:** the reminder notification carries no task content (access may have changed since it was set; opening the task goes through normal authorisation).

**Behaviour changes:** (1) `IN_REVIEW` joins the status enum (forward-only: PostgreSQL cannot drop an enum value, so the migration has no down-script); (2) a task that has a reviewer can no longer be completed by `PATCH status=DONE` (409 `review_required`) - tasks without a reviewer behave exactly as before; (3) the assignee and reviewer may comment without holding `task:manage`; (4) new events `task.review_requested`, `task.reviewed`, `task.commented` (in-app notifications to reviewer / assignee / participants); (5) new audit actions `task.review_approved|returned`, `task.commented`, `task.attachment_added|removed`, `task.reminder_created|cancelled|sent`. **Least privilege:** the runtime role cannot update/delete comments, update attachments or delete reminders (default privileges grant full DML to new tables; the migration revokes it).
**Known limits:** reminders are one-shot and in-app (e-mail/SMS channels arrive with the notification channel port); no automatic due-date reminders yet; the evidence link between tasks, documents and workflows is generalised in increment 7 (`evidence_link`).

### 6.1 Verification of the task engine (adversarial pass) - findings and fixes
The increment was re-examined as an attacker and as an unreliable infrastructure would behave. Findings, all fixed in migration `20260104000500` and the task service, each with a test that failed before the fix:

| # | Finding | Fix | Test |
|---|---|---|---|
| F1 | **Append-only records were protected by triggers only.** Default privileges give new tables full DML to the runtime role, so `audit_event` still held `UPDATE`/`DELETE` and `document_version` `DELETE`. A trigger is the second line of defence; privileges must be the first | `REVOKE UPDATE, DELETE, TRUNCATE` on `audit_event`, `DELETE, TRUNCATE` on `document_version` | `tests/db/privileges.test.ts` (effective privileges via `has_table_privilege`, real-connection attempts, matrix that fails when a new append-only table is not covered) |
| F2 | **A poisoned reminder was retried on every sweep and could starve newer ones** (oldest-first batches) | `attempts`, `last_error`, `retry_at`; exponential backoff (30 s ... 1 h), abandoned (cancelled + audited `task.reminder_failed`) after 8 attempts | `tests/platform/task-reminders.test.ts` (starvation with batch size 1, abandonment) |
| F3 | **The assignee could clear the reviewer, then complete the task directly** (reviewer changes were allowed outside `IN_REVIEW`) | the assignee can neither change nor remove the reviewer of their own task (API and trigger); managers who are not the assignee keep that authority, audited with before/after | `tests/api/task-review-security.test.ts` |
| F4 | **Two simultaneous review decisions could both "win"** (read-then-write) | conditional `UPDATE ... WHERE status='IN_REVIEW' AND reviewer_user_id = actor`; the loser matches no row (409) | same file (parallel approve/return, triple approve) |
| F5 | **Anyone who could manage tasks could nominate any colleague as reviewer** | a reviewer must hold `workflow:review` for the company (at nomination **and** again at decision time) | same file |

**What was verified and held:** reviewer identity comes only from the authenticated session (body fields naming a user are rejected, identity-looking headers are ignored, another organisation's session sees 404); the database refuses completion of a reviewed task from any other context (other organisation's context, system context, user-only context, no context, another user, skipping `IN_REVIEW`); a reviewer who left the organisation or lost the review permission cannot decide, and the owner can return the task and nominate someone else (no dead end); reminders survive a crash after the notification was written (both roll back), a killed database connection mid-transaction (lock released, no duplicate, next sweep delivers once), concurrent cancel-vs-sweep (never both sent and cancelled), and N parallel workers (exactly once).

**Residual trust boundary (documented, not removable at the database):** the database trusts the application to assert the tenant and user (`app.organisation_id`, `app.user_id`) - the same model that row-level security relies on everywhere. Code that can execute arbitrary SQL as the runtime role can therefore claim any identity. Controls: no raw SQL built from strings anywhere (`tests/unit/architecture.test.ts` forbids `$queryRawUnsafe`/`$executeRawUnsafe`), only the task service writes tasks, the runtime role owns nothing, has no `SECURITY DEFINER` helpers and cannot disable triggers/RLS or change grants (`tests/db/privileges.test.ts`). Production-only hardening still to do: separate database credentials for API and worker, `pgaudit`, and connection-level alarms (tracked for the production gate).

## 7. Document management (specification §6) and the evidence graph (cross-platform §6) - design
Written **before** implementation because it adds new architecture (ADR-32 .. ADR-34). Nothing here introduces accounting behaviour.

### 7.1 Scope
| Spec item | Design |
|---|---|
| upload, versioning, company | unchanged (kept as is; `document_class` stays the API field name) |
| **document type** | `document_type` REFERENCE table (code, name; seeded, SELECT-only for the runtime role); `document.document_class` becomes a foreign key to it. Registry mirrored in `@uk/contracts` (`DOCUMENT_TYPES`); a test keeps the two identical. Existing free-text values are carried over as types |
| **folders** | `document_folder`: tree per company (or organisation-level), unique sibling names, depth <= 8, no cycles, a folder and its parent belong to the same company (trigger), delete only when empty. A document's folder must belong to the document's company (trigger) |
| **accounting period** | `document.period_id` (composite FK); the period must belong to the document's company (trigger) |
| **metadata** | `description`, `document_date`, `reference`, `labels` (<= 10), and a bounded `metadata` object (<= 20 keys, scalar values, <= 8 KB) for type-specific attributes. `PATCH /documents/{id}` edits them, audited with before/after |
| **permissions / visibility** | Per-company `document:*` permissions stay the base. Each document is `STANDARD` or `RESTRICTED`. A restricted document is visible only to its creator, to users with an explicit `document_access` grant, and to holders of the new `document:confidential` permission for that company. Everyone else gets **404** (no existence oracle) from every path: documents, versions, downloads, task attachments, workflow evidence, evidence links, extraction text. Implemented once in the central authoriser (`AccessContext.canReadDocument` / `documentWhere`); making a document restricted needs `document:upload`, relaxing it or managing grants needs `document:confidential` |
| **OCR-ready pipeline** | `OcrProvider` port (AIProvider -> OCRProvider -> Embedding/Search, specification §10) in `@uk/platform`, a deterministic fake for tests, `OCR_PROVIDER=none` by default. After a version becomes AVAILABLE the worker queues `document.ocr` **only if** the organisation's `documents.ocr` feature flag is on (default off, re-checked when the job runs). Output goes to `document_extraction` (text, pages, confidence, engine, status); it is **data, never a decision** - nothing is posted or filed from it. Extraction text is as visible as its document |
| **immutable filing evidence** | `POST /documents/{id}/evidence-lock` (`evidence:lock`): locks one AVAILABLE version (its SHA-256 is recorded), sets a retention date (default 6 years, never in the past). From then on - enforced by database triggers, not only by the API - the document accepts no new versions, no edits, no archive and cannot be deleted; the lock cannot be undone through the application. Legal hold may still be added |
| **evidence graph** | `evidence_link` (source -> target, kind): typed, same-company, immutable once written (revoke records who/when/why; rows are never deleted). Entity types are a registry in `@uk/contracts` that later versions append to (journal, bank transaction, report, tax return, filing ...). Both ends must be readable by the caller and in the same company; task attachments and workflow evidence write their links in the same transaction as today's rows |

### 7.2 New permissions (all COMPANY scope)
`document:confidential`, `evidence:lock`, `evidence:read`, `evidence:manage`. Matrix: owner/admin/partner all four; manager `document:confidential`, `evidence:read`, `evidence:manage`; accountant and bookkeeper `evidence:read`, `evidence:manage`; reviewer `evidence:read`; client viewer none. Anti-escalation (`canGrantRole`) applies unchanged.

### 7.3 Decisions and trade-offs
* **ADR-32 visibility is enforced in the application, centrally.** Row-level security keeps isolating tenants; per-document visibility depends on roles and grants that live in the application's authorisation model, so duplicating them in SQL would create two sources of truth. The price: every code path that reads documents must use the central helper - an architecture test forbids reading `document` rows outside the documents module and the helper.
* **ADR-33 filing evidence is locked at the database.** A filed return's evidence must survive application bugs and operator mistakes, so the lock is a trigger-enforced one-way door (like append-only audit). Object-level immutability (S3 Object Lock, COMPLIANCE mode) is a production-gate item and unchanged by this increment.
* **ADR-34 the evidence graph is polymorphic without foreign keys.** One table links any entity type to any other, which keeps V1+ from adding a link table per feature, but PostgreSQL cannot enforce that the target exists. The service validates both ends at write time through a per-type resolver, links are never deleted (only revoked), and an integrity query is part of the tests. Entities are never hard-deleted by the application, so links cannot dangle.
* OCR text is sensitive: stored per tenant under RLS, never logged, size-capped, and produced only for organisations that opted in through the flag (this is also the per-organisation gate REV-13 asked for before any external provider is enabled; no external provider exists yet).

### 7.4 Compatibility and risk
Additive migrations (`20260104000600`, `20260104000700`); existing documents become STANDARD, unlocked, in no folder. API responses gain optional fields; existing fields and routes are unchanged. Behaviour changes: `documentClass` must be a known type (422 `unknown_document_type`; previously any string); the runtime role loses `DELETE` on `document` (documents are archived, never deleted). **High-risk step:** adding the foreign key on `document.document_class` - the migration first inserts any existing distinct value as a type, so it cannot fail on legacy data.

| # | Finding | Fix |

### 7.7 Known limits (deliberate)
* No real OCR engine: the pipeline is *ready* (port, flag, store, job, visibility); a real engine is a V6 deliverable behind the port. No Embedding/Search provider port yet (specification section 10 lists it; it is outside the eight approved Tranche A items - flagged for the final gate).
* **Immutable filing evidence is immutable in the database, not yet in object storage**: S3 Object Lock (COMPLIANCE mode) is Terraform that has never been applied to a real account (production gate). Until then a privileged operator with bucket access could still delete the object; the application and the database cannot.
* Folders organise; they do not secure: visibility is per document, not per folder.
* The evidence graph cannot enforce that a polymorphic target exists (no foreign keys): it is validated at write time and by an integrity test; entities are never hard-deleted by the application.
* Document retention schedules per type (V0-S8) are not part of this increment.

## 8. Observability (Manifest technical contract; OBS-02, OBS-03, OBS-05) - design
Written before implementation. Scope is the approved Tranche A minimum; OpenTelemetry spans/exporters, dashboards, SLOs and k6 smoke tests remain Tranche B (OBS-04, XP-12) and are listed as deliberately deferred.

### 8.1 Scope
| Need | Design |
|---|---|
| **Access logs** (OBS-02) | One structured log line per request when it finishes: method, **route template** (never the concrete path, so no ids or query strings), status, duration, response size, correlation id, user/organisation ids, trace id; level by outcome (2xx/3xx info, 4xx warn, 5xx error; health/metrics probes at debug). No request or response bodies, no headers, no query string. IP and user agent only when `AUDIT_CAPTURE_DEVICE_METADATA` is on (same lawful-basis switch as the audit trail) |
| **Metrics** (OBS-03) | A small in-process registry in `@uk/core` (counter, gauge, histogram; no new dependency) with two renderings: Prometheus text and **CloudWatch Embedded Metric Format** (one JSON log line, extracted by CloudWatch with no agent). HTTP: request count and latency histogram by route template and status class; login failures (401/429 on the login route). Platform gauges collected from the database: outbox pending / failed / oldest-unprocessed age / in-flight, jobs by status (QUEUED, RUNNING, FAILED, DEAD), due task reminders. Process: event-loop lag, memory. The worker emits EMF every `METRICS_EMF_INTERVAL_MS`; the API exposes `GET /metrics` **only when `METRICS_TOKEN` is set** (bearer, constant-time comparison; otherwise 404) |
| **Alerting** (OBS-05) | Terraform: an SNS topic (e-mail subscription variable) and CloudWatch alarms on the EMF metrics (failed outbox events, outbox lag, dead jobs, 5xx rate, login-failure burst) and on native ECS/ALB/RDS metrics (unhealthy targets, ALB 5xx, CPU, memory, database connections and free storage). Alarms treat missing data as breaching for the heartbeat metric, so a silent worker is an alarm. Validated by `terraform validate` in CI; never applied (production gate) |
| **Readiness detail** | `/healthz` stays a pure liveness probe. `/readyz` keeps failing (503) only for the dependencies the API cannot serve without (database, Redis) and reports **degraded** (still 200) when the outbox lags beyond `READINESS_OUTBOX_LAG_SECONDS` or jobs are DEAD, with the figures in the body (no tenant data) |
| **`job_record.company_id`** | Jobs gain a nullable, composite-FK company so queue state can be read per company and filtered by the caller's company access; set by the document pipeline. Behaviour change: `GET /jobs` hides jobs of companies the caller cannot read |
| **Trace context** | W3C `traceparent` is accepted (or generated), kept in the request context and logs, stored on `job_record.trace_id` and restored in the worker, so one request can be followed API -> job -> worker in the logs. This is propagation, not an OpenTelemetry SDK |

### 8.2 Decisions and trade-offs
* **ADR-35 metrics without a vendor SDK.** EMF-over-logs needs no agent or sidecar in ECS and no new supply-chain surface; Prometheus text is available for local use. The cost: no exemplars/spans and metric math is limited to what CloudWatch provides. An OpenTelemetry SDK + ADOT collector can replace the renderers later behind the same registry.
* **Label discipline.** Labels are route templates, methods, status classes and queue/status names only - bounded sets. A test fails if a concrete id or query string appears in a label, because one leaked label per tenant would make the metric unusable and could leak tenant ids into a shared system.
* **`/metrics` is off by default** and needs a shared-secret bearer even when on; platform gauges are aggregate counts (no tenant data).
* Gauges that describe global state are produced by the worker (single writer per interval) to avoid double counting from N API tasks; the API reports its own process and HTTP metrics.

### 8.3 Compatibility and risk
