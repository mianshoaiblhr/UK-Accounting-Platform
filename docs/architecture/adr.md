# Architecture Decision Records (V0)

| # | Decision | Why / alternatives |
|---|---|---|
| 1 | **Modular monolith** (api + worker + web, shared packages) | Future ledger needs transactional consistency; microservices rejected. |
| 2 | **Pooled DB + RLS**, tenant = `organisation_id`, transaction-local `app.organisation_id`/`app.user_id` | Schema/DB-per-tenant rejected (ops cost). Fails closed without context; composite FKs stop cross-tenant references. |
| 3 | **Practice-first single model**: Organisation(PRACTICE\|BUSINESS)→Companies; `company_scope ALL\|ASSIGNED` | Direct business = one-company org. No second product architecture. **Amended by ADR-23/24:** a distinct `practice` level now sits between organisation and company, and access is granted at organisation, practice and company level. |
| 4 | **Prisma 6** + hand-written SQL appended to migrations (RLS, grants, triggers, exclusion constraint, seed) | Prisma 7/8 not adopted (driver-adapter churn, release candidates). Schema is source of truth; custom SQL is documented drift. |
| 5 | **Opaque server-side sessions** (hashed, idle+absolute expiry), not JWT | Instant revocation, no key rotation; works unchanged with future OIDC logins because providers only prove identity. |
| 6 | **IdentityProvider interface**; lockout/MFA/session policy applied by `AuthService` for every provider | Entra/Google/Auth0 = one new class + `user_identity` row. |
| 7 | **TOTP implemented in-house** (RFC 6238, tested against RFC vectors), secrets AES-256-GCM, replay protection, recovery codes | Avoids a dependency for ~40 lines; MFA type is an enum, so WebAuthn adds a verifier, not a flow change. |
| 8 | **BullMQ + `job_record`** as durable source of truth + sweeper | Redis may lose data; Postgres record lets us re-dispatch. Sensitive payloads encrypted in Redis and Postgres. |
| 9 | **Ports/adapters** for storage, email, antivirus, identity. AWS knowledge only in `createStorage/createEmail` and Terraform | Moving cloud or adding DR changes env vars, not code. |
| 10 | **Residency guard** in app config and Terraform (`allowed_regions`) | Production refuses to boot outside approved regions; DR region must also be approved. |
| 11 | **Audit append-only in DB** (grants + triggers), written in the business transaction | Cannot be altered by the app role or the owner without disabling triggers. |
| 12 | **Vitest everywhere**; Playwright *library* inside Vitest for E2E | One runner. Integration files run serially (shared DB/Redis). |
| 13 | Turborepo dropped; `pnpm -r` topological build | Not needed at this size. |
| 14 | **OpenAPI in V0**: contract generated from the running Nest app; request schemas ARE the runtime zod validators; route docs table enforced complete by tests; spec committed and drift-checked | Contract is a first-class asset. |
| 15 | **Transactional outbox in V0**: event row written in the business transaction; polling relay with `SKIP LOCKED`; BullMQ hand-off; consumer idempotency via `event_consumption` in the consumer's transaction | Guarantees no lost/phantom events; at-least-once delivery, exactly-once effect. |
| 16 | **Layered login throttling** (IP+account pair, IP, account-under-attack with trusted-IP carve-out) replaces per-account lockout | Stops brute force without enabling lockout DoS; no account enumeration. |
| 17 | **Auth tables outside tenant RLS** is a documented, tested exception (`security-architecture.md` §1.1) | RLS there adds complexity/failure modes with no isolation benefit. |
| 18 | **Real-infrastructure test layer**: shared adapter contract suites run against fakes and real S3/ClamAV; CI requires them (`INFRA_REQUIRED=1`); S3 protocol via moto (MinIO no longer distributed), ClamAV via the official image | Fakes cannot drift from reality. |
| 19 | **Workflow engine, tasks, notifications, integration + AI abstractions** are V0 foundations; AI output is proposal-only behind a human-approval workflow | Reusable by V1+ without re-implementing approvals or leaking vendor SDKs. |
| 20 | Migrations non-destructive by default; destructive ones need an approval marker + verified backup id | `docs/runbooks/migrations.md`. |
| 21 | Deferred: SSO providers, WebAuthn, outbox retention/cleanup job, Redis-backed edge rate limits | Not needed for V0. |
| 22 | **Naming convention** (one, before V1): singular snake_case tables; `<entity>_id` columns; join/grant tables are named for their level - `organisation_membership`, `practice_membership`, `company_membership`; constraints/indexes `<table>_<columns>_fkey\|key\|idx`. Renamed only the ambiguous tables (`membership`, `company_assignment`); **pluralising every table was rejected** (touches ~30 tables, policies, FKs and tests for no functional gain) | Specification table list uses plural names; functionally equivalent. Renames are metadata-only `ALTER ... RENAME` (data, RLS, grants, FKs preserved), flagged by the migration-safety test and approved with a backup-required marker. |
| 23 | **Practice is a distinct entity under Organisation**, not a specialised/nested Organisation. Canonical ownership: `organisation` owns and bills; `company.organisation_id` is the owner, `company.practice_id` the managing practice (required for PRACTICE organisations, forbidden for BUSINESS, enforced by trigger + composite FK); `organisation.type` is immutable. | One tenant boundary (RLS, outbox, audit unchanged); no cross-tenant relationships; direct businesses need no pretend practice; multiple practices per organisation supported; cross-organisation engagements can be added later as an explicit grant table without changing the hierarchy. See `v0-hierarchy-and-authorisation-design.md`. |
| 24 | **Layered authorisation with one central authoriser**: platform role (no tenant access) -> organisation membership (role + reach) -> practice membership -> company membership. Permissions have a scope (ORG/PRACTICE/COMPANY); for a company the most specific grant wins and replaces broader ones (can restrict or extend); deny by default; anti-escalation at every level. Implemented once as pure functions in `@uk/contracts/authz` + `AccessContext` in the API; an architecture test forbids services re-implementing role/scope logic. | Least privilege and testability; avoids per-controller drift. Trade-off: "replace, not union" means a company grant can lower access - intended and documented. |
| 25 | **Reusable workflow foundation**: versioned definitions (`standard_workflow` DRAFT->IN_PROGRESS->REVIEW->APPROVAL->COMPLETED/REJECTED + `generic_approval` maker/checker); per-transition permission evaluated for the instance's company; segregation of duties across ALL attempts; mandatory comments/evidence per transition; explicit reassignment and reopen (retry); **a database trigger refuses any state change without a recorded transition in the same transaction**. Stricter (accounting/statutory) workflows only add controls. | "No silent transitions" is enforced below the application, not just by convention. |
| 26 | **AI proposal state model**: `SUGGESTED -> UNDER_REVIEW -> ACCEPTED \| REJECTED` (workflow `ai_proposal_review` v2), provenance persisted (provider, model, prompt version, confidence, source evidence, run), human decision and *application* recorded separately; `ACCEPTED` applies nothing - the owning service applies it through its own authorised path and calls `recordApplication`. Other AI use cases register their own workflow type. v1 (legacy) instances remain decidable. | AI never posts/files; recommendation and human decision stay distinguishable. |
| 27 | **Migrations must work for a non-superuser owner** (production `uk_migrator`): FORCE RLS applies to table owners, so data statements lift RLS on the specific table for the migration transaction only and restore it. The two earlier seed/UPDATE migrations were corrected (no persistent environment had applied them); a test builds the whole schema as a non-superuser. | Found during this work: previously the seed would have failed (or silently no-op'd) outside CI's superuser. |
| 28 | **`audit:read` is company-scoped** (was organisation-wide). Audit events carry `company_id`; readers see their companies' events plus organisation-level events only if their organisation role holds `audit:read`. Before/after, reason and source workflow added; IP/device capture switchable. | Least privilege per company; completes specification §8. See `v0-tranche-a.md` §2. |
| 29 | **Outbox ordering is per aggregate**, enforced by head-only relay publication + a consumer-side guard; poison events block only their aggregate; cleanup deletes processed events after a retention window and can never delete unprocessed ones. | Strict global ordering would serialise the whole platform; per-aggregate order is what business logic needs. See `v0-tranche-a.md` §3. |
| 30 | **Reference data is a protection class of its own** (`REFERENCE`: global, no `organisation_id`, `SELECT`-only for the runtime role, changed by migrations). Tax jurisdictions are effective-dated with a non-overlap exclusion constraint; companies hold the jurisdiction *code* (a code is not unique over time, so a trigger checks existence rather than a foreign key). Contacts are generic and org-level or company-level; addresses belong to exactly one owner. | Keeps tenant tables and global reference data separable and testable; avoids V1 semantics in V0. See `v0-tranche-a.md` §5. |
| 31 | **Task review is a database-enforced rule; reminders are swept, not queued.** A task with a reviewer completes only from `IN_REVIEW` and only by that reviewer (API + trigger reading the acting user from the tenant context; segregation of duties: reviewer != assignee). Reminders are rows delivered by a worker sweeper (system-context `SELECT`, then one tenant transaction per reminder with `FOR UPDATE SKIP LOCKED`), exactly once, atomically with the notification; the notification carries no task content. `IN_REVIEW` is a forward-only enum addition. **Verification addendum:** the assignee cannot change or remove their own reviewer (otherwise: clear, then complete); a reviewer must hold `workflow:review` at nomination and at decision; decisions are conditional updates (no double-win); failing reminders back off and are abandoned after 8 attempts; append-only tables lose `UPDATE`/`DELETE`/`TRUNCATE` privileges (not just triggers) | Review/sign-off (V7/V8) must not depend on UI discipline; per-reminder delayed jobs would add a second source of truth and lose reminders on Redis loss. Tenant isolation is preserved: the system context never writes, each write runs under the owning organisation's RLS. |
| 32 | **Per-document visibility is enforced centrally in the application** (`STANDARD` / `RESTRICTED`; restricted = creator, explicit grant, or `document:confidential`; everyone else gets 404 from every path) | Visibility depends on roles/grants that live in the authorisation model; mirroring them in RLS would create two sources of truth. Tenant isolation stays in RLS. Guarded by an architecture test: documents are read only through the documents module / central authoriser. |
| 33 | **Filing evidence is locked by database triggers**: one AVAILABLE version (SHA-256 recorded), retention date, no new versions / edits / archive / delete, no unlock through the application | A filed return's evidence must survive application bugs and operator error. S3 Object Lock COMPLIANCE mode is a production-gate item. |
| 34 | **Evidence graph is one polymorphic table** (`evidence_link`: typed source -> typed target, same company, immutable, revoked not deleted, ends validated through a resolver registry) | Avoids a link table per feature in V1+; PostgreSQL cannot enforce polymorphic existence, so validation is in the service plus an integrity test; entities are never hard-deleted. |
| 35 | **Metrics without a vendor SDK**: an in-process registry rendered as Prometheus text (opt-in `/metrics` behind a bearer token) and as CloudWatch Embedded Metric Format log lines; bounded labels only (route templates, status classes, queue/status names); trace context is propagated (W3C `traceparent` -> logs -> job -> worker) but spans/exporters (OpenTelemetry + ADOT) are deferred | EMF needs no agent/sidecar and adds no supply-chain surface; label discipline keeps cardinality bounded and keeps tenant ids out of shared systems. OpenTelemetry can replace the renderers later behind the same registry. |
| 36 | **`job_record` is the integration job table.** No separate `integration_jobs`: status, attempts, exponential backoff, dead-lettering, sensitive-payload encryption, idempotency and operator retry already exist once; it carries organisation, company, trace and correlation ids. The listed V0 test (transient failure, retry with backoff, success) runs against a flaky operation of the development mock provider. | A second table would duplicate the runtime's bookkeeping and give each integration two places to look. See `v0-tranche-a.md` §9.1. |
| 37 | **Workflow deadlines are columns on the instance plus a swept one-time notification**, not a timer queue. `due_at` (optional `slaHours` per definition), overdue = past due and not terminal, `workflows_overdue` gauge, `FOR UPDATE SKIP LOCKED` sweeper with backoff and abandonment, changing the due date re-arms the notification. | The database is the single source of truth and survives Redis loss; same proven pattern as task reminders (ADR-31). See §9.2. |
| 38 | **Notification channels are a port; planning is transactional, delivery is not.** `NotificationChannel` + registry; `in_app` inline in the caller's transaction, other channels via `notification_delivery` rows swept by the worker; e-mail hands off to the existing `email.send` job with an idempotency key; SMS/WhatsApp are disabled stubs; per-user opt-in preferences (e-mail default off); content-free e-mail. | Adds channels without touching callers, never performs network I/O inside a business transaction, and introduces no new outbound personal data until a user opts in. See §9.3. |
| 39 | **Retention is classified in reference data before V1 data exists** (`retention_category`, `retention_rule`; every document type and table must map to a category; registry == database, tested). Periods are PROVISIONAL pending the DPO/legal decision; no purge or erasure behaviour is introduced. | Ledger and filing data created by V1 is classified from day one; enforcement (S4(b)) is a separate, later, approved item. See §9.4. |
| 40 | **UI strategy (DEC-002): V1 is API-first; the V0 UI screens are built in parallel behind feature flags.** Priority: usable end-to-end bookkeeping workflows. A screen's flag is declared in the registry (`packages/contracts/src/features.ts`) when the screen is started and stays off until it is complete; UI tests run against the real API, authorisation rules and tenant boundaries (no mocked authorisation). MAN-DOD-05 and XP-11 stay open until screens exist and pass accessibility checks. | Keeps the accounting core moving without hiding unfinished UI behind a "done" claim. See `decision-log.md`. |
| 41 | **Retention and privacy stay provisional (DEC-003).** All retention categories remain PROVISIONAL; S4(b) (purge jobs, irreversible erasure rules, production retention enforcement) is not to be implemented or enabled before the schedule and the lawful-basis decisions are approved; development uses synthetic/test data only; IP address and user-agent retention is flagged for privacy review (`docs/legal/retention-verification-schedule.md`, section 2). A schema or configuration for retention is never evidence that a legal requirement is implemented. | Prevents an engineering default from becoming an unreviewed legal position; a test keeps the schedule and the registry in step and fails if a category is marked confirmed without a decision. |
| 42 | **Naming deviations accepted (DEC-004): `job_record` is the integration job table (ADR-36), the permission catalogue is code (V0-1.5), `ai_run` is the AI request log.** Preserved: retry behaviour, idempotency, status/error tracking, tenant/company scoping, correlation/trace ids; implementation, tests, OpenAPI and documents stay consistent. **A separate model is justified only if** (a) integrations gain provider-side long-running operations whose lifecycle (remote ids, webhooks, polling) does not fit the job states; (b) a statutory submission needs a record with a different retention or immutability class than operational jobs (a filing record is a domain table, not an `integration_jobs` table); (c) per-connection quota/metering queries cannot be served by indexes on `job_record` at its real volume (then partition or split by queue first); (d) third parties (V12 marketplace) must register permissions dynamically or tenants define custom permission types (then a `permissions` table, with the code catalogue as seed); (e) AI prompts/responses must be stored with a different privacy or retention class than the hashed `ai_run` log. Any such change is a new ADR and a migration, not a silent rename. | Records when the trade-off should be revisited so the deviation is a decision, not an accident. |
| 43 | **Deferrals and gates (DEC-005, DEC-006).** S3 (device identity, new-device alert, admin kill-switch) and S7 (embedding/search ports) are deferred to later tranches and revisited when their dependency and acceptance criteria are defined; baseline authentication, session revocation, authorisation and tenant isolation must not be weakened by the deferral. AWS deployment and production hardening remain explicit gates; Terraform `validate` in CI is not evidence that infrastructure was applied or verified; V0 approval is not production approval. | Keeps "ready to build V1" separate from "ready to run for customers". |
| 44 | **Ledger model (V1-M1).** `journal` + `journal_line` are the accounting truth: money is `NUMERIC(19,4)` (decimal strings in the API, never floats), one currency per journal = the company's base currency (no FX in M1), per-company journal numbers from a locked counter, the period is resolved from the journal date, posted journals are immutable (privileges first, triggers second) and corrected only by a reversal journal linked by `reverses_journal_id` (at most once; a reversal is not itself reversed). No draft state in the ledger: drafts belong to source documents. | The ledger must be small, strict and boring; every richer behaviour lives in source modules that post through one door. See `v1-plan.md` 3. |
| 45 | **PostingService is the sole writer of the ledger (V1-M1).** Lives in `packages/accounting`; one transaction runs a fixed validator chain (actor, permission, source, period, accounts, currency/amounts, balance, tax slot) and then inserts with a transaction-local posting flag that database triggers require; an architecture test names it as the only code touching `journal`/`journal_line`; AI actors are refused; repeats are idempotent by key. A deferred constraint trigger re-checks balance at commit; lines can only be added in the journal's own transaction; the period row is locked `FOR SHARE` so a concurrent close cannot race a posting; `OPENING_BALANCE` (the one manual source allowed on control accounts) is accepted only on the first day of the first period. The flag is application-asserted (same trust boundary as tenant context): honest limit documented. | Enforces manifest controls 1-5 and 10 below the application where possible and says plainly where it cannot. |
| 46 | **Chart of accounts (V1-M1).** Company-scoped; type and subtype registries; reporting mapping from a versioned registry; accounts are deactivated (active dates), never deleted; code/type/control flags are immutable once used; **control accounts cannot be posted to by manual journals** (sub-ledger integrity) - a deliberate, documented control that a later decision may relax with an explicit permission; a default UK chart template (versioned) can initialise an empty chart. | Control accounts must equal their sub-ledgers; making that structural avoids reconciling it away later. |
| 47 | **Period states and close controls (V1-M1).** OPEN <-> CLOSED -> LOCKED -> CLOSED with a database-enforced transition graph, `period:manage` for close/reopen and the new `period:lock` for lock/unlock, mandatory reasons for reopen/lock/unlock, audited with before/after and emitted as events; posting requires OPEN. Further close checks are added by the milestone that creates the data they check. | Manifest control 8; separates routine closing from the stronger act of locking. |
| 48 | **Reports read the ledger only (V1-M1, applies to M5).** The trial balance (and later P&L and balance sheet) aggregate `journal_line`; no report reads a source document table; every figure carries the parameters to drill into the general ledger and each ledger line names its journal and source. Materialised balances are deferred until measured. | Manifest: no alternative accounting truth; universal drill-down. |

## Known limitations (honest list)
- Login volume cap per IP can affect users behind a shared NAT during an attack (pair/IP/account layers otherwise target the attacker only).
- Global auth tables are protected by application-level controls only — see `security-architecture.md` §1.1 (tested).
- Terraform passes `fmt` + `validate` but has not been applied to a real AWS account. The migration runs as a pipeline step (`infra/db/migrate.sh`), deliberately not provisioned as infrastructure.
- Real S3/ClamAV tests run in the `infra` layer (`pnpm test:infra`); locally against a stand-in S3 server and a minimal-signature clamd, in CI against MinIO + official ClamAV.
